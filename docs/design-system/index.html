Principles

what dt-solver looks & feels like
01 · density
Every pixel earns its place.

Engineers scan waveforms — we use 9.5–12.5px type and 2px radii so more signal fits in view without feeling cramped.

02 · mono for numbers
Times, slack, signal IDs are tabular.

Geist Mono on anything you'd compare row-to-row. Geist Sans for prose, labels, and titles.

03 · status is color
Emerald passes. Rose fails. Amber waits.

A 10% wash + 30% border + 300-weight text — the same recipe everywhere a result is shown.

04 · sharp not soft
2px radii. Hairline borders. No drop shadows in chrome.

Shadows reserved for modals only. Surfaces stack via background lightening, not elevation tricks.

Motion & voice

small movements · precise words
motion
  • noneStatus changes (pass → fail). Numbers update with no easing — they're data.
  • tint · 120msHover row tint, button background. transition: background-color 120ms
  • reveal · 160msTrash icon fade-in on row hover. opacity 0 → 100
  • chevron · 200msSection collapse rotation. transform: rotate(90deg)
  • no slideModals appear instantly with backdrop blur — feel like a tool, not an app.
voice & copy
  • "live · pass" — uppercase, mono, separated by middots. Never "Pass!"
  • "1 constraint violated" — count the thing, name it, end the sentence.
  • "all constraints satisfied" — lowercase summary state in footers.
  • "≥ 30 ns" — inequality + value + unit. Never round; trust the solver.
  • "try a different edge direction" — diagnostic, not apology, in the empty-state overlay.
  • "solver: cycle-accurate · iter 1 / 1" — pretend the user is reading a debugger status bar.
